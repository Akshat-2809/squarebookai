# Squarebook — squarebookai.com

Marketing site for Squarebook, a collections and billing-dispute platform for Indian lenders. It is a production port of the approved homepage design, plus the "Request a pilot" form backend.

Everything lives in one Next.js 16 app in [`web/`](web/). The pilot form is handled by a **Server Action** in the same app, so there is no separate API service. It writes to Postgres and sends emails through Resend.

    ├── drizzle/                 SQL migrations (generated by drizzle-kit, commit these)

## Local setup

Requirements: Node 20.9 or later, and a Postgres database.

```bash
cd web
npm install
cp .env.example .env.local      # then fill in the values
npm run db:migrate              # creates the pilot_requests table
npm run dev                     # http://localhost:3000
```

Postgres for local work, pick one:

- **Docker:** `docker run --name sqb-pg -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=squarebook -p 5432:5432 -d postgres:17`. This matches the default `DATABASE_URL` in `.env.example`.
- **Neon:** create a free project and use a dev branch's connection string.

If `RESEND_API_KEY` is empty, the form still works and the emails are skipped with a log line.

## Environment variables

| Variable | Required | Notes |
|---|---|---|
| `DATABASE_URL` | yes | Postgres connection string. Use Neon's **pooled** URL on Vercel. Without it, the form shows an error asking people to email instead. |
| `RESEND_API_KEY` | for email | From resend.com → API Keys. |
| `EMAIL_FROM` | for email | e.g. `Squarebook <support@squarebookai.com>`. The domain must be verified in Resend. |
| `NOTIFY_EMAIL` | for email | Inbox that receives each new pilot request. |
| `IP_HASH_SALT` | yes in production | Random string (`openssl rand -hex 32`). IPs are stored only as salted hashes, for rate limiting. |

## How the pilot form works

1. `PilotForm` posts to the `requestPilot` Server Action (`src/app/actions/pilot.ts`). It also works with JavaScript disabled.
2. If the honeypot field `website` is filled, the action returns a normal-looking success and stores nothing.
3. zod validates the input: name, email format, organisation, and `accountsBand`, which must be one of `under-5k`, `5k-50k`, `50k-5l`, `over-5l` (the four options in the design's select).
4. Rate limit: 5 requests per IP per hour, counted in Postgres. This works across serverless instances.
5. The request is stored in `pilot_requests`. The `reference` column is generated by Postgres from the id: `SQB-0001`, `SQB-0421`, and so on, still zero-padded after 9999. The receipt shows it in place of the design's hard-coded `CHK-0421`.
6. Both emails (the internal notification to `NOTIFY_EMAIL` and the confirmation to the requester) are sent with `after()`, once the response has gone out. An email failure is logged and never fails the request.
7. UI states: idle; submitting (button disabled, spinner, screen-reader announcement); success (the printed receipt with the real reference, which receives focus); error (inline message, field-level errors, typed values kept).

## Deploy to Vercel

1. Push the repo to GitHub, GitLab or Bitbucket, then in Vercel choose **Add New → Project** and import it.
2. Set **Root Directory** to `web`. The framework preset (Next.js) and the build command are detected automatically.
3. **Database:** Project → **Storage** → **Create Database** → **Neon (Postgres)**, and connect it to the project. This adds `DATABASE_URL`, and the other Neon variables, to the environments you choose.
4. Add `RESEND_API_KEY`, `EMAIL_FROM`, `NOTIFY_EMAIL` and `IP_HASH_SALT` under Settings → Environment Variables, for Production (and Preview if you want previews to send emails).
5. Run the migration once against the production database, from your machine:
   ```bash
   cd web
   DATABASE_URL="<Neon connection string from Vercel>" npm run db:migrate
   ```
   Repeat this whenever you add a migration. If you use Neon preview branches, run it against those as well.
6. Deploy. Preview deployments serve a `Disallow: /` robots.txt, so they stay out of search results.

## Connect squarebookai.com (bought on GoDaddy)

### 1. Point the domain at Vercel
1. In Vercel: Project → **Settings → Domains** → add `squarebookai.com`, then add `www.squarebookai.com`. When asked, choose to **redirect `www` to the apex**. The canonical URLs, sitemap and OG tags all use `https://squarebookai.com`.
2. Vercel then shows the exact DNS records to create. Use those values; they are typically:
   - apex `squarebookai.com`: **A** record, host `@`, pointing to the IP Vercel shows (often `76.76.21.21`)
   - `www`: **CNAME** record, host `www`, pointing to the target Vercel shows (often `cname.vercel-dns.com`)
3. In GoDaddy: **My Products → squarebookai.com → DNS → Manage DNS**.
   - Delete GoDaddy's default "Parked" **A** record for `@`, and any existing `www` CNAME, so they don't conflict.
   - Add the A and CNAME records exactly as Vercel shows them, with TTL 1 hour or lower.
4. Back in Vercel, wait for both domains to show **Valid Configuration**. HTTPS certificates are issued automatically.

### 2. Let Resend send as @squarebookai.com
1. In Resend: **Domains → Add Domain** → `squarebookai.com` (or a subdomain such as `mail.squarebookai.com`).
2. Resend lists the DNS records to add: an MX record and SPF TXT for the sending subdomain, a DKIM TXT record, and optionally DMARC. Add each one in GoDaddy's DNS manager exactly as shown, then click **Verify** in Resend.
3. Set `EMAIL_FROM` to an address on the verified domain.

If you also want to *receive* mail at support@squarebookai.com and sampannakanungo@squarebookai.com, set up a mailbox provider (Google Workspace, Zoho, etc.) and add its MX records for `@`. Resend only sends.

## Fidelity notes (vs. the approved design, `Main.dc.html`)

The homepage was compared side by side with the design in Chrome at 1440px and 390px:
- **Full page:** identical layout, with every section at the same top and height. Pixel difference is 0.03% (1440) and 0.11% (390).
- **Interactive states:** all 6 Desk tabs, every instalment option and all 5 How-it-works steps match.
- **Hero animation:** follows the design's timeline.

Intentional differences:
- The contact email is `support@squarebookai.com`, and it is a `mailto:` link.
- "Privacy · Terms · Grievance officer" are links to the new pages.
- Accessibility additions with no visual change: tab panels have ids and `aria-controls`, plus arrow, Home and End key navigation; FAQ questions sit inside `h3`s and their answers are `inert` while closed; footer column titles are `h2`s styled exactly like the design's `h4`s, to keep the heading order valid; the form has labels, `aria-invalid`, live regions and a visually hidden honeypot.
- Fonts are self-hosted with `next/font` and include the latin-ext subset, so `₹` renders in Geist and Familjen Grotesk as it does in the design.
- One quirk was reproduced on purpose. In the design's own renderer, `.rowt span` also styles the hero ledger titles (12.5px grey), and `.track span` also styles the integration pills (22px with a yellow square). The port keeps both, because that is how the approved design looks.

Worth a decision later (kept as designed): at 390px the nav wraps onto two lines, because the logo and the "Request a pilot" button don't fit side by side.

## Lighthouse (mobile, local production build)

Best Practices 100, SEO 100, Accessibility 97, Performance 94–95 across several runs. CLS is 0 and TBT is 30–80 ms. The simulated LCP is about 3.0s, set by the size of the Next.js/React runtime under Lighthouse's slow-4G model; in a real Chrome load the LCP is about 0.2s. The only accessibility warnings come from the design's intentionally dimmed states: unlit ledger rows, inactive scrollytelling steps, and the 12px step labels at 4.44:1 contrast. Re-run Lighthouse against the Vercel URL after deploying; Brotli and edge caching there usually improve on local numbers.
